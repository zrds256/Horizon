**「背景」** Java 的 sealed 类和接口用于把继承关系限制在作者声明的许可子类型内，从而让编译器知道一个类型的所有可能变体。配合 Java 21 起标准化的 switch 模式匹配，编译器可以在编译消费者代码时检查分支是否穷尽，而不必写 default。运行时若出现未匹配任何分支的值，即使该 switch 在编译时被视为穷尽，也可能抛出 MatchException，这也是 sealed API 演进时需要关注的兼容性背景。

**「社区讨论」** 评论中有人批评这种“二进制兼容但可能运行时失败”的演进方式不理想，主张新增 permitted 子类应当打破消费者与生产者 API JAR 的二进制兼容性；也有人赞赏 Java 的密封类与模式匹配设计相对 C\# 更易解释。讨论还提到 Java 的递归模式、可能仍处于预览的字面量模式，以及 TypeScript 的 ts-pattern 等替代方案。

### [舍弃非必要需求，才能设计优雅系统](https://seangoedecke.com/what-requirements-dont-you-have/) ⭐️ 6.0/10

**「背景」** 作者提出，设计软件时，明确自己不必满足哪些需求，与列出要满足的需求同样重要；若试图同时满足速度、并发、数据新鲜度、简单接口等所有要求，往往连可工作的系统都做不出来。

**「方案」** 他的核心观点是，优雅系统常通过主动放弃某个需求，把弱点转成优势：Unicorn 不提供共享可变状态、也不处理慢客户端，因而可用独立进程隔离，并把请求直接排到 Unix socket；S3 放弃多键原子更新，换来按 blob 存储、减少跨分区协调；StatsD 默认用 UDP，接受可能丢数据以降低网络开销；边缘缓存、SQLite 和 Cursor 也分别以数据可能过期、不支持并发写、接受高尾延迟，换取速度、运维简单或扩展性。作者强调，识别可放宽的需求同时需要技术与业务判断，工程师和产品经理之间的信任很难建立，而单人开发者或初创公司因两种判断集中于一人，反而可能做出大公司难以做出的取舍。LLM 编程代理则因 RLVR 训练和对“评分器”的执念、缺乏业务上下文，常自行引入不必要的并发锁和一致性检查，把四行改动膨胀成千行；因此作者认为代码评审并未死亡，并会在提示中说明可接受缓存短暂陈旧，评审 Go 代码时先扫描多余的 mutex 或间接层。

**「启示」** 作者的核心结论是，保持系统优雅需要持续追问哪些需求其实不必满足，并有意识地接受陈旧数据、偶发尾延迟和更少协调；否则需求会固化，系统最终被检查和锁拖垮。
